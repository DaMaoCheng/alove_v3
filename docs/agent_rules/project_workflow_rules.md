# 项目推进、版本与分期规则

本文件用于新增功能、大改动、多轮迭代、旧项目交接、版本隔离、分期推进和本地方案文档落地。涉及具体 Git 分支、提交、合并、回滚或发布操作时，必须另外确认 Git 操作边界。

## 1. 触发条件

出现以下任一情况时，必须进入项目推进评估，而不是直接改代码：

- 新增功能，不只是单点小修；
- 大改动、多文件改动或跨模块改动；
- 同一需求进入第二轮以上迭代；
- 同一问题第二次以上修复仍未确认解决；
- 用户明确表示后续还会继续推进；
- 接手旧项目、已有历史方案或交接上下文；
- 当前改动可能影响架构、数据流、接口链路、页面结构、权限、埋点或长期维护。

## 2. 已有方案优先

接手已有项目或已有方案时，必须先读取并理解现有资料，包括但不限于：

- README；
- 需求文档；
- 技术方案；
- 设计稿；
- TODO；
- issue；
- PR 描述；
- 历史计划；
- 交接说明；
- 已有分期文档；
- 项目树、版本树、更新日志、BUG 日志或维护记录。

不得忽略已有方案重新设计。读取后必须判断：

- 原方案是否仍然适用；
- 当前需求和原方案是否一致；
- 是否存在过期、冲突或缺失的信息；
- 本次改动应该延续原方案，还是需要调整方案；
- 如果要调整，必须说明调整原因、影响范围和回退方式。

## 3. 不懂就问

- 需求、业务规则、视觉标准、数据含义、交互预期或完成标准没有 100% 清晰时，必须先问用户。
- 禁止用“我以为”“通常来说”“看起来应该”代替确认。
- 如果用户描述中有多个可能方向，要列出不同理解，让用户确认。
- 如果无法从现有文档确认规则来源，要明确说明缺口，不要把推测写成事实。

## 4. 分期方案

遇到新增功能、大改动或多轮迭代时，必须先结合项目实际情况拆分阶段。

分期方案至少包含：

- 每一期目标；
- 每一期修改范围；
- 每一期不做什么；
- 每一期验证标准；
- 主要风险；
- 回退点；
- 是否需要分支、worktree 或阶段性 commit。

用户确认分期方案后，先将方案落地为本地文档，再按文档推进。后续如果需要偏离方案，必须先说明原因和影响，等待用户确认。

## 5. 版本树与检查点

这里的“版本树”指用 Git 分支、worktree、阶段性 commit 或清晰文档，把不同阶段隔离开，方便回退、对比、审查和交接。

进入以下状态时，必须评估是否建立版本树：

- 新增功能预计超过一次提交；
- 同一需求进入第二轮以上迭代；
- 同一问题第二次以上修复；
- 大改动涉及多个模块或多类文件；
- 需要同时探索两种以上实现方向；
- 用户需要保留当前稳定状态。

如果项目已使用 Git，优先考虑：

- 新建独立分支；
- 新建 Git worktree；
- 每个阶段形成可说明的 commit checkpoint；
- 每轮迭代前确认当前工作区是否干净；
- 避免在主分支或主工作区里无限叠补丁。

如果项目没有 Git，必须先说明风险，并建议至少创建本地备份点或阶段文档。未经用户确认，不要擅自初始化 Git 或大规模迁移目录。

## 6. 既有记录更新

如果项目已有项目树、分期方案、版本树、任务看板、维护记录或交接文档，必须遵守：

- 改动前先读取原有格式和最近记录；
- 不得另起一套记录格式；
- 阶段推进后及时更新状态、进度、检查点和下一步；
- 完成阶段后标记完成结果和验证结果；
- 如果实际推进偏离原方案，必须记录偏离原因、影响范围和用户确认情况；
- 如果不确定应更新哪份记录，先列出候选文档并询问用户，不要跳过。

## 7. 分批推进闭环

当需求需要分批推进时，必须遵守：

- 先确认当前批次目标，不得同时推进多个批次；
- 当前批次必须拆成可独立验证的小部分；
- 每完成一个小部分，必须验证该部分功能完整性、相邻影响和必要回归范围；
- 验证通过后，按项目既有规则更新版本号、更新日志、BUG 日志、项目树、分期文档、任务看板或维护记录；
- 分批推进、大改动或核心链路改动时，每个批次进入下一批次前，必须按 `docs/agent_rules/review_rules.md` 完成必要审查；审查发现阻塞问题时，不得进入下一批次；
- 完成验证和记录更新后，才能进入下一小部分或下一批次；
- 如果验证失败，必须先修复或回到上一个检查点，不得继续推进后续内容；
- 如果实际推进偏离原分批方案，必须先说明原因、影响范围和建议调整，等待用户确认。

## 8. 本项目记录落点

`alove-page-rebuild` 默认记录落点：

- 更新日志：`logs/updates/YYYY-MM-DD.md`
- BUG 日志：`logs/bugs/YYYY-MM-DD.md`
- 版本节点：`docs/releases/*.md`
- 分期方案：`docs/superpowers/plans/*.md`
- 需求规格：`docs/superpowers/specs/*.md`

分批推进时，每个批次完成后必须按实际影响更新这些记录。没有对应业务改动时，不要硬写业务日志；但如果有功能、接口、数据、页面或发布行为变化，不能跳过记录。

## 9. 推进纪律

- 每个阶段只做该阶段范围内的事，不抢跑后续阶段。
- 每个阶段完成后，必须对照分期文档验证目标是否达成。
- 如果阶段验证失败，先回到上一个可确认检查点重新判断。
- 如果连续两次偏离预期，必须暂停推进，复盘方案是否需要调整。
- 后续推进时优先读取已经落地的分期文档，不要重新凭记忆规划。
