# 架构与代码组织规则

本文件用于新模块开发、目录调整、文件拆分、重构、公共模块抽离和大文件治理。

新增功能、大改动、多轮迭代、旧项目交接或分期推进时，先读取 `docs/agent_rules/project_workflow_rules.md`，再决定架构落点。

写入新代码、追加逻辑、拆解复杂文件、治理重复逻辑、发现职责混乱或评估是否需要解耦时，先读取 `docs/agent_rules/code_quality_rules.md`，再决定是否需要调整结构。

## 1. 分层判断

新增功能、修复问题、做优化时，必须先判断代码应该落在哪一层：

- 页面层：页面结构与页面级交互组织；
- 组件层：可复用 UI 组件；
- 功能模块层：某一业务功能的完整实现；
- 接口 / 服务层：请求、数据访问、接口封装；
- 状态层：全局或局部状态管理；
- 工具层：纯函数、格式化、转换、公共判断；
- 配置 / 常量层：配置项、枚举、常量；
- 类型层：类型定义；
- 埋点层：事件追踪、上报封装、埋点常量。

## 2. 模块组织原则

- 禁止把项目主要逻辑全部塞进单一 js / ts 文件。
- 主入口文件只负责初始化、路由挂载、模块装配和页面启动，不应承载所有业务细节。
- 默认优先按“功能 / 模块”组织代码，而不是无脑按文件类型堆目录。
- 一个业务功能相关的页面、组件、hooks、service、store，可以优先围绕该功能归档。
- 只有明确可复用的内容，才放到全局公共目录。
- 新增需求时，优先复用现有模块；如果没有合适模块，应新建模块或新建文件，而不是继续往旧的大文件里追加。

## 3. 拆分信号

如果一个文件同时承担多种职责，应视为需要拆分的信号，例如：

- UI 渲染；
- 数据请求；
- 状态处理；
- 业务规则判断；
- 数据转换；
- 埋点逻辑；
- 配置与常量；
- 工具函数堆积。

重复两次以上的逻辑，必须主动评估是否抽离：

- 重复 UI 片段，抽成公共组件；
- 重复交互逻辑，抽成 hooks 或独立逻辑模块；
- 重复请求逻辑，抽成 service；
- 重复数据处理，抽成 utils；
- 重复埋点逻辑，抽成 analytics 模块。

如果同一个文件在项目推进中被连续多次追加逻辑，必须主动评估是否需要拆分。

## 4. 复杂遗留代码拆解

当需要拆解复杂遗留代码、复杂大文件、职责混乱模块或长期堆叠文件时，必须遵守：

- 拆解前先梳理当前文件职责、入口、出口、状态来源、数据流和真实使用链路；
- 功能复杂、影响范围大或缺少测试保护时，必须先评估快照、备份、独立分支、worktree 或阶段性 commit checkpoint；
- 不要一次性大搬迁。必须按功能边界、调用链或职责边界拆成可验证的小部分；
- 每拆解一个小部分，必须完成真实链路自检，确认原有功能、关键交互、接口调用、状态流转和相邻模块没有被破坏；
- 验证通过后，才能继续拆下一部分；
- 如果验证失败，必须先修复或回到上一个检查点，不得继续叠加拆解；
- 如果拆解过程中发现原判断错误、职责边界不清或影响范围扩大，必须暂停并重新说明拆解方案、风险和下一步；
- 拆解后如果项目已有项目树、分期文档、更新日志或维护记录，必须按原格式更新拆解进度、验证结果和遗留问题。

拆解目标是降低维护风险，不是为了目录更好看而移动文件。没有验证闭环的拆解视为未完成。

## 5. 本项目重点关注的大文件和高风险链路

`alove-page-rebuild` 中，以下类型改动尤其要先评估拆分边界和检查点：

- 聊天页、语音、实时通话、主动消息等状态链路；
- 后台管理台模板、控制器、商品选择器、广告活动页面；
- 商品搜索、商品气泡、商品跟进回复、广告投放链路；
- 数据库初始化、seed、migration 和运行配置装配；
- 旧项目迁移过来的服务逻辑或多轮迭代后持续变大的文件。

这些链路不能只靠 `node --check` 判断成功，必须结合对应自检、真实接口或真实页面闭环。

## 6. 依赖方向

- 依赖方向必须清晰。
- 上层可以调用下层，业务模块不要反向耦合基础模块。
- 避免循环依赖，避免改一个文件牵动大量无关代码。

## 7. 默认目录结构

若项目未指定结构，默认参考如下目录组织：

```txt
src/
  app/            项目入口、初始化、路由
  pages/          页面级文件
  components/     通用组件
  features/       按业务功能拆分的模块
  services/       接口请求、数据访问
  store/          状态管理
  hooks/          复用逻辑
  utils/          工具函数
  constants/      常量
  config/         配置
  types/          类型
  styles/         样式
  analytics/      埋点与事件追踪
```

如果项目较小，也至少要做到：

- 页面和组件分离；
- 请求逻辑和页面逻辑分离；
- 工具函数和业务代码分离；
- 常量、类型、埋点不要散落在页面文件里。

## 8. 执行边界

- 不要为了“先跑起来”牺牲后续维护性。
- 除非用户明确同意，否则不要采用“先全写在一个文件里，以后再拆”的方式。
- 未经确认，不要擅自引入新框架、新状态管理方案、大型依赖或大规模结构迁移。
- 如果确实有必要，必须先说明为什么需要、收益、代价、影响范围和回退方式。
- 当单个业务文件已经明显过长、阅读成本过高、修改风险变大时，即使当前需求还能勉强继续往里写，也默认优先评估拆分。
- 当新增功能或大改动需要跨多个模块推进时，不要直接在现有结构里连续叠加修改；必须先评估分期方案、版本隔离和阶段性检查点。
