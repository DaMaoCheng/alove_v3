# Chat Voice Rules

本文件约束聊天发送节奏、语音上传、AI 回复顺序、ASR 和前后端队列行为。

## 1. 文字消息节奏

如果需求涉及“延迟生成”“消息聚合”“生成期间排队”，必须把：

- 用户消息保存
- 等待计时
- AI 回复生成
- 生成期间新增消息处理

拆成明确阶段，不能混在一次请求里凭感觉处理。

像 `1.5` 秒等待重算、生成期间排队这类逻辑，必须有明确状态和定时器规则，不允许只靠页面显示凑效果。

## 2. 语音链路顺序

语音功能默认按两段理解：

1. 上传音频并得到用户消息
2. 基于该用户消息生成 AI 回复

UI 顺序必须和后端真实顺序一致：

- 先出现用户语音转写消息
- 再出现 AI 思考中的占位状态
- 最后出现 AI 回复

不能出现“用户消息还没落库，AI 占位先出来”的错序。

## 3. ASR 规则

- ASR 需要尽量保留原始语言和书写形式。
- 英文单词和中英混说，不应随意音译成中文。
- 如果出现高频音译误差，先评估 prompt 是否足够明确；仍不稳时，增加轻量、可解释的后处理规则。
- 后处理必须保守，不能大面积改写用户真实话语。

## 4. 商品与语音/聊天共用规则

如果商品气泡后的补充回复会进入：

- 普通文本聊天
- 语音回复 TTS
- 主动消息

则清洗器和确定性规则应复用同一份，不允许三条链路各自散落一套相近但不一致的逻辑。

## 5. 前后端顺序一致性

当用户要求某种体验顺序时，必须同时检查：

- 后端接口是否支持这个阶段拆分
- 前端 UI 是否按真实状态切换
- 是否存在重渲染导致占位状态丢失
- 是否存在生成期间再次发送消息导致乱序

不能只改前端动画，不改真实消息链路。

## 6. 不允许的行为

- 为了赶进度把排队、去重、节奏控制都压成单个大函数且无状态说明
- 只修页面，不修后端接口顺序
- 只修接口，不验证前端真实气泡顺序
- 用“看起来差不多”替代真实链路自检
