# Service Runtime Rules

本文件约束服务运行态、自检前后的进程确认、端口确认、健康检查和真实接口验证。

## 1. 端口和服务基线

默认本地基线：

- App: `http://127.0.0.1:4173`
- MySQL: `127.0.0.1:3307`

修改服务端路由、server service、数据库迁移、构建入口、前端请求配置后，不能只说“已重启”或“脚本显示 ready”。

## 2. 重启后的强制确认

每次相关修改后，至少确认：

1. 当前监听 `4173` 的 PID 是哪个进程
2. 该 PID 是否确实来自当前项目目录
3. `api/health` 或同类健康接口正常
4. 新增或修改的真实接口返回了新行为，而不是旧行为或 404
5. 如果页面仍表现旧逻辑，先排查旧进程、缓存、登录态，而不是直接认为代码没生效

## 3. 常见错误归类

看到页面问题时，必须先判断属于哪一类：

- 旧 Node 进程还在跑旧代码
- 脚本误报 ready，但后台进程已退出
- MySQL 没启动或 migration 没跑完
- 新路由已存在，但因为未登录返回 401
- 浏览器页面还拿着旧前端缓存
- 用户当前登录态不对，导致接口被拦截

禁止把这些运行态问题直接误判为“代码逻辑没写”。

## 4. 接口验证边界

- 新接口不能只靠前端页面间接验证，至少要有一轮直接接口或服务函数验证。
- 返回 401/403 时，先判断是不是登录态问题，不能直接说“接口不存在”。
- 返回 404 时，先确认服务是否已加载新路由，再查请求路径。
- 对需要管理员态的接口，验证时要明确说明是否使用了管理员登录态。

## 5. 浏览器与真实页面验证

当任务涉及后台 UI、聊天页面、商品气泡、广告活动、语音、主动消息、登录态时，最终应至少做一次真实页面或真实接口闭环验证。

如果因为缺少登录态无法做页面验证：

- 先向用户索要账号；
- 不猜密码；
- 必要时说明“当前只完成代码和接口层验证，页面验证卡在登录态”；
- 不要把未完成的页面验证写成已完成。

## 6. 本地测试账号规则

- 优先向用户索要当前可用账号。
- 不在规则、日志、release、脚本里沉淀账号密码。
- 若临时创建本地测试账号，必须说明用途，验证后清理，并在最终汇报中写清楚是否清理。
