# 代码质量与复杂度控制规则

本文件用于防止复杂度堆积、重复逻辑、职责混乱、过度工程、无关重构和任务失焦。

核心原则：持续识别复杂度，但只在触发条件成立时做最小拆解；拆解必须服务当前需求，并通过真实链路验证。

## 1. 触发边界

出现以下任一情况时，进入本文件规则：

- 新增代码、新功能、新模块或新结构；
- 向复杂文件、大文件或职责混乱文件追加逻辑；
- 拆解复杂文件、治理重复逻辑或评估是否需要解耦；
- 同类逻辑已经重复两次以上，本次可能出现第三份；
- 当前改动可能改变模块职责、数据流、状态流、依赖方向或复用边界；
- 用户明确要求改善代码质量、降低复杂度、拆分文件、解耦或治理历史问题。

以下情况不需要专门进入代码质量治理流程：

- 只改文案、注释、配置值或静态数据；
- 只修复明确的一行或少量局部 bug，且不新增职责；
- 只按现有模式补一个同类字段、枚举、映射或样式值；
- 只更新测试快照、锁文件或生成物；
- 当前文件职责清晰，改动不会增加复杂度、重复逻辑或新的依赖方向。

即使不进入本文件流程，也仍需遵守总纲中的外科手术式修改和真实验证要求。

## 2. 最小实现阶梯

进入本文件规则后，写代码前必须按顺序判断：

1. 这个需求是否真的需要新增实现，还是可以通过现有功能、配置、文档或操作流程解决；
2. 项目里是否已有相同或相近能力，可以直接复用或小幅扩展；
3. 标准库、语言内建能力或平台原生能力是否已经能解决；
4. 项目已安装依赖是否已经提供稳定能力；
5. 是否可以用更小的局部改动完成，而不是新增模块、抽象层或通用框架；
6. 是否可以先实现最小可用路径，再根据真实重复和真实复杂度决定是否抽象；
7. 只有以上路径都不合适时，才写最小可行实现。

不得为了更短代码牺牲安全、错误处理、可读性、真实验证、项目记录或用户明确要求。最小实现不是临时凑合，也不是跳过必要边界处理。

## 3. 写代码前结构检查

写入新代码、追加逻辑或修改复杂文件前，必须先检查：

- 是否已有相同或相近的函数、组件、service、hook、常量、类型或工具方法；
- 新逻辑应该放在现有模块，还是新建小模块；
- 当前改动是否会让文件职责更混乱；
- 是否会制造第三份以上重复逻辑；
- 是否存在更小、更清晰、更贴近现有架构的落点；
- 如果不拆，后续维护成本是否明显增加；
- 如果拆，是否能限制在当前需求范围内并完成验证。

如果结构检查发现明显风险，必须先说明风险、建议处理方式和验证方式。

## 4. 复杂度红线

准备继续向现有文件追加逻辑时，如果命中以下任一情况，必须暂停直接追加，并评估最小拆解方案：

- 单文件同时承担 UI、状态、请求、业务判断、数据转换、配置、埋点等多种职责；
- 当前改动会继续增加第三种以上职责；
- 同一个文件已经连续多轮被追加逻辑；
- 新增代码会让文件职责边界更模糊；
- 为完成当前需求，需要反复在同一文件多个无关区域跳转修改；
- 已经出现重复逻辑、重复状态、重复请求或重复判断；
- 修改一个小功能会牵动多个无关功能；
- 文件过长，导致无法快速理解主要职责和调用链。

命中红线不等于立刻大重构。Agent 必须先判断是否需要拆解、拆解是否服务当前需求，以及是否有足够验证手段。

## 5. 允许拆解的触发条件

只有以下情况之一成立，才允许把拆解纳入本次任务：

- 不拆会直接增加本次需求的实现风险；
- 不拆会导致新增逻辑继续污染复杂文件；
- 当前需求本身就是重构、拆分、解耦或架构治理；
- 职责混乱导致无法安全定位本次改动；
- 同类逻辑已经重复两次以上，本次会出现第三份；
- 用户明确要求改善结构；
- 当前改动需要新增可复用模块，否则会产生明显重复。

如果只是看到历史代码不顺眼，但不影响当前需求，不得擅自拆解。

## 6. 最小拆解原则

拆解必须遵守：

- 只拆与本次需求直接相关的职责边界；
- 优先抽离最小稳定单元；
- 优先复用项目已有目录、命名、状态管理和模块模式；
- 不做全项目翻新；
- 不顺手改无关命名、格式、样式、目录结构或文案；
- 不引入新框架、新状态管理方案或大型抽象；
- 拆解后必须保持原行为不变，除非用户明确要求改行为；
- 每拆一部分必须真实链路自检，确认正常后才能继续下一部分。

## 7. 防止过度工程

出现以下倾向时，必须收缩方案：

- 为一次性需求创建多层抽象；
- 为未来可能发生的需求预留大量接口、配置或扩展点；
- 把简单条件判断改成复杂策略模式、插件系统或框架式设计；
- 把局部问题扩大成全局架构治理；
- 修改范围明显超出用户需求；
- 新增抽象后调用方更难理解，而不是更简单。

如果更简单的方案能满足当前需求并保持可维护性，必须选择更简单方案。

## 8. 防止任务失焦

当发现旧问题、坏味道或可优化点时，必须区分：

- 本次必须处理：不处理会阻塞当前需求或导致明显风险；
- 本次建议处理：处理成本低，且能明显降低当前改动风险；
- 本次只记录提醒：与当前需求无直接关系；
- 本次禁止处理：会扩大范围、改变行为、影响发布或需要用户决策。

未经用户确认，不要把“本次只记录提醒”的内容变成代码改动。

## 9. 本项目重点防线

`alove-page-rebuild` 中，以下链路尤其容易因为局部改动变复杂：

- 聊天消息、语音、实时通话、主动消息调度；
- 商品触发、商品搜索、商品气泡、商品跟进回复；
- 广告活动、商品快照、投放记录和后台表单；
- 数据库 seed、migration、站点配置和运行态诊断；
- 后台管理台模板和控制器。

这些链路新增逻辑前必须优先复用已有 service、自检和数据结构。不能为了当前一个按钮、字段或特殊场景新增一套平行实现。

## 10. 验证闭环

任何拆解、抽离、解耦或复杂度治理都必须完成验证闭环：

- 拆解前明确原功能链路和关键验证点；
- 拆解后验证原功能仍然正常；
- 涉及 UI 时验证真实交互和响应式边界；
- 涉及接口时验证请求参数、返回映射、错误状态和空状态；
- 涉及状态时验证状态初始化、切换、重置和异常路径；
- 验证失败时先修复或回到检查点，不得继续叠加拆解。

没有真实链路验证的拆解视为未完成。
