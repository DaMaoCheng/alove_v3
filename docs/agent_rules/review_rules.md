# 审查、第一性原理与对抗式验证规则

本文件用于复杂 Bug、连续失败、核心链路、大改动、线上风险、分批推进检查点、方案审查和代码风险审查。

核心原则：先找根因，再验证风险；低风险用自检，高风险用多 Agent 互评；审查不能变成扩大需求、无关重构或拖慢普通小改的理由。

## 1. 触发条件

出现以下任一情况时，必须进入本文件规则：

- 复杂 Bug、连续失败、根因不明；
- 线上事故、生产风险、远程服务器或托管平台；
- 核心业务链路、主流程、数据入库、消息推送、通知、日报、报表；
- 权限、支付、账户、隐私数据、客户数据、订单、库存；
- 队列、worker、定时任务、批处理、爬虫、导入导出、自动化任务；
- 缓存、重试、并发、幂等、回滚、补偿机制；
- 大改动、多模块改动、分批推进阶段完成点；
- 用户明确要求第一性原理、对抗式审查、多 Agent 审查或代码风险审查。

## 2. 本项目核心链路

`alove-page-rebuild` 中，以下链路默认视为核心链路：

- 登录、账号、站点归属、角色可见性和权限；
- 聊天发送、语音、实时通话、主动消息、AI 回复生成；
- 商品搜索、商品气泡、商品跟进回复、商品点击和曝光统计；
- 广告活动匹配、投放去重、商品快照、delivery 记录；
- 数据库 migration、seed、站点配置、运行态诊断；
- 后台管理台中会影响前台用户体验或运营数据的页面。

这些链路进入下一批次或宣称完成前，必须根据风险级别做对抗式自检或多 Agent 互评。

## 3. 第一性原理排查

遇到复杂 Bug、连续失败、架构设计、性能问题、数据异常、线上事故或核心链路异常时，不能只修表层症状。必须从第一性原理重新判断：

- 这个系统最基本的目标是什么；
- 数据从哪里来，到哪里去；
- 哪些条件必须成立；
- 哪个假设被打破；
- 当前修复是在治本，还是只是在绕过症状；
- 如果只修当前表象，未来是否会在其他入口再次爆发。

如果发现根因在更底层，必须说明：

- 表层修复方案；
- 根因修复方案；
- 两者风险、成本、影响范围；
- 推荐方案和验证方式。

第一性原理不是大重构许可证。只有当表层修复无法可靠解决当前问题，或根因会反复导致同类事故时，才允许建议根因修复。扩大范围前必须先说明方案、风险和回退方式，等待用户确认。

## 4. 对抗式审查

对抗式审查用于主动寻找当前方案、代码、数据链路和发布路径中的漏洞。它不是普通总结，也不是重复自检。

审查时必须站在反方视角，主动证明当前实现可能出错，重点检查：

- 恶意或异常输入；
- 超大数据、空数据、重复数据、脏数据；
- 网络失败、接口超时、第三方返回异常；
- 重试是否造成死循环、重复副作用或资源耗尽；
- 时间、时区、未来时间、过期数据；
- 权限、身份、越权访问；
- 缓存、队列、worker、定时任务的异常状态；
- 部分成功、部分失败、回滚和补偿；
- 日志、告警、可观测性是否足够；
- 是否存在性能炸弹、内存风险、并发竞争或状态污染。

审查输出必须包含：

- 发现的问题；
- 风险等级；
- 复现或触发条件；
- 影响范围；
- 建议修复方式；
- 是否阻塞继续推进。

## 5. 对抗式自检

以下情况可以由当前 Agent 自行完成对抗式自检：

- 单文件小改；
- 局部 bug 修复；
- 非核心 UI 调整；
- 不涉及权限、支付、生产数据、队列、worker、定时任务、批处理或线上发布；
- 改动范围清晰，影响范围可直接验证；
- 已有测试或真实链路能覆盖主要风险。

自检必须至少检查：

- 正常路径；
- 空状态；
- 错误状态；
- 边界输入；
- 相邻模块是否受影响；
- 是否引入重复逻辑或职责混乱。

如果自检发现风险扩大，必须升级为多 Agent 互评或暂停询问用户。

## 6. 多 Agent 互评

以下情况必须使用多 Agent 互评，不能只做当前 Agent 自检：

- 涉及生产环境、线上发布、远程服务器或托管平台；
- 涉及支付、权限、账户、隐私数据、客户数据、订单、库存；
- 涉及核心业务链路、主流程、数据入库、消息推送、通知、RSS、日报、报表；
- 涉及队列、worker、定时任务、批处理、爬虫、导入导出、自动化任务；
- 涉及重试、缓存、并发、幂等、回滚、补偿机制；
- 大改动、多模块改动、分批推进中的阶段完成点；
- 同一问题连续两次以上仍未确认解决；
- Agent 自检发现影响范围扩大或存在无法确认的风险。

## 7. 多 Agent 分工

多 Agent 互评必须有明确分工，不得多个 Agent 做同一类泛泛检查。常用分工：

- 架构与职责边界：检查模块职责、依赖方向、重复逻辑、过度耦合；
- 数据与状态链路：检查数据来源、映射、状态流转、空值、脏数据、未来时间；
- 异常输入与边界：检查超大输入、恶意输入、重复请求、缺失字段、异常格式；
- 安全与权限：检查越权、敏感数据、token、密钥、隐私、访问边界；
- 性能与资源：检查死循环、内存、并发、缓存、队列积压、worker 重试；
- 发布与回滚：检查部署影响、版本记录、日志、回滚路径、告警和可观测性。

每个 Agent 必须输出独立结论。主 Agent 汇总时必须区分：

- 已确认问题；
- 潜在风险；
- 误报或无需处理；
- 必须修复后才能继续；
- 可记录为后续技术债。

## 8. 审查边界

对抗式审查不是扩大需求的理由。审查发现的无关历史问题，默认只记录，不得擅自修复。

多 Agent 互评用于高风险场景。普通小改不得默认启动大规模并行审查。

审查输出必须服务于当前目标。不得为了证明审查充分而制造无关工作。

如果审查发现阻塞问题，必须先修复或回到检查点；如果只是潜在技术债，记录后继续当前任务。
