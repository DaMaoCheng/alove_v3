# Testing Debugging Rules

本文件约束 `alove-page-rebuild` 的排查和验证节奏，重点防止补丁叠补丁、错把运行态问题当代码问题，以及自检与真实行为脱节。

复杂 Bug、连续失败、线上事故、根因不清，或需要第一性原理排查和对抗式审查时，先读取 `docs/agent_rules/review_rules.md`。

## 1. 排查顺序

出现问题时，优先按这个顺序查：

1. 任务理解是否正确
2. 真实项目目录是否正确
3. 推进过程中一旦出现问题、异常、Bug、返工信号或验证不通过，先检索 `logs/bugs/` 和相关 `logs/updates/`，确认是否已有相同现象、历史根因、修复方式、验证记录或未完成风险
4. 当前进程是否是新代码
5. 运行配置和数据是否满足前置条件
6. 真实接口行为是什么
7. 前端页面是否只是缓存或登录态问题
8. 最后才是代码逻辑缺陷

不得忽略已有 Bug 日志重新从零排查或继续推进；如果历史记录与当前现象相似但不完全一致，必须说明相同点、差异点和是否能复用历史修复思路。

## 2. 补丁失败处理

如果同一个文件的补丁连续两次失败：

- 必须暂停继续盲打
- 重新读取准确行号、函数边界、上下文
- 说明当前失败原因是上下文不匹配、函数已变化还是文件过大
- 必要时改成更小补丁或结构化替换

禁止在同一处反复输出“重新插入”“再试一次”而不改变方法。

## 3. 二次返工规则

同一个问题被用户第二次指出，或者同一问题连续两次没有彻底修好时，必须重新做根因分类，至少覆盖：

- 方向判断错了
- 只修了表层，没修链路
- 数据/配置没同步
- 服务未重启
- 自检口径不对
- 用户真实期望和当前实现不一致

此时不能继续默认按原方向叠补丁。

## 4. 自检脚本规则

- 新增功能或修复缺陷，优先先补失败自检，再实现。
- 但要先确认自检真的在测目标缺口，不要让测试先失败在无关前置条件上。
- 如果自检依赖源码字符串，做模块拆分前必须先升级自检读取范围。
- 不要让字符串扫描型自检因为文件拆分而误报失败。

## 5. 最终验证分层

默认按四层验证：

1. `node --check` 或等价语法检查
2. 目标自检脚本
3. 真实接口或服务函数验证
4. 真实页面/真实用户链路验证

如果第 4 层因登录态等原因无法完成，必须明确说明，不得写成“已完整验证”。

## 6. 页面截图优先级

用户提供截图时：

- 先把截图当作高优先级证据
- 不能用“我的脚本通过了”直接反驳截图
- 先检查服务是否旧进程、页面是否旧缓存、数据是否不满足，再回到代码层

## 7. 真实验证注意事项

- 需要登录态时优先向用户索要账号
- 不猜账号密码
- 不把临时测试账号长期留在数据库里
- 如果使用临时账号验证，完成后要清理并在汇报里说明
