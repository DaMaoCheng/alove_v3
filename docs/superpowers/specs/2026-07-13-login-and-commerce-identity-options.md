# AIOVE 登录与外部商城身份方案评估

状态：`Draft / TBD`
更新时间：2026-07-13
用途：汇总可选登录、身份验证和商城订单获取方案，供产品确认；本文不代表已批准实施。

## 1. 目标与当前事实

本议题需要同时解决三个目标：

1. 用户从站点前台进入 AIOVE 后，尽量不创建和记忆另一套密码。
2. AIOVE 能在用户完成可信身份验证后，取得所属站点的真实购买记录并建立初步画像。
3. 登录和订单数据按 `site_id` 隔离，不能因为邮箱相同自动跨站点合并。

当前事实：

- `Current`：AIOVE 已有自己的账号、登录注册、Google 登录和游客认证承接。
- `Current`：游客认证成功后可承接当前站点的聊天、附件、语音、图片和通话记录。
- `Current`：站点 Shopify 接入目前只用于可信商品读取；尚未接入 Shopify 客户登录、客户资料或订单同步。
- `TBD`：FKK 使用新版还是旧版 Shopify Customer Accounts、可申请的 API scope、受保护客户数据权限和 OAuth 客户端配置尚未核实。

## 2. 所有方案共同遵守的规则

- 外部商城密码不得导入、记录、转发或由 AIOVE 代为验证。
- 邮箱相同只能作为候选匹配，不能在用户完成验证前直接认领订单。
- AIOVE 必须保留自己的本地 `user_id` 和登录 session；外部授权成功不等于浏览器永久登录。
- 若要准确取得购买记录，内部至少保存 `site_id + provider + external_customer_id/subject + user_id` 的可审计映射。它不要求两个系统共享密码，也不代表商城可以修改 AIOVE 账号。
- 客户、订单和画像只能由后端可信接口导入；前端参数、模型判断和用户口述不能作为已购证明。
- 原始订单与推导画像分开保存。画像必须记录来源和更新时间，不能覆盖或伪造订单事实。
- 登录返回后，必须回到原站点、原前台和原游客会话；跨站点身份冲突必须明确拒绝或进入人工处理，不能静默合并。
- 所有“邮箱是否存在、是否购买过”的未认证响应使用统一文案，避免泄露客户存在性和购买情况。

## 3. 方案总览

| 方案 | 用户以后如何登录 | 如何取得订单 | 主要条件 | 适用判断 |
| --- | --- | --- | --- | --- |
| A. AIOVE 邮箱 + 密码 | 输入 AIOVE 密码 | 另做商城身份验证或订单认领 | 无外部登录依赖 | 可保留为现有基线，但不满足最低操作成本 |
| B. AIOVE 邮箱验证码 | 每次由 AIOVE 发送验证码 | 验证邮箱后按站点匹配/同步订单 | 邮件发送、验证码风控 | 简单稳定，可作为 OAuth 不可用时的 fallback |
| C. Shopify Customer Account OAuth/OIDC | 点击“Continue with {site}”，由 Shopify 验证；授权有效时可快速返回 | 使用授权客户身份读取客户范围数据，或以 customer ID 调用受控后端订单同步 | 新版 Customer Accounts、client ID、callback、scope 和数据权限 | 当前首选候选，前提是 FKK 配置核实通过 |
| D. 一次性邮箱验证认领 | 认领后使用 AIOVE 密码、验证码或 Google 登录 | 首次验证后导入历史订单；可不持续连接 Shopify 身份 | 可查客户/订单、邮件验证 | 适合一次性迁移，不等于持续免密码登录 |
| E. 预导入待认领账号 | 用户收到激活邮件后设置 AIOVE 登录方式 | 导入时写入外部客户与订单快照 | 合法取得全量客户数据、去重和激活流程 | 批量迁移可用，但会产生大量未激活记录 |
| F. Google/Apple 等社交登录 + 订单认领 | 使用社交账号登录 AIOVE | 仍需单独验证商城邮箱或 OAuth | 社交登录配置 | 登录方便，但不能单独证明商城订单归属 |
| G. 两边共用同一 IdP | 两边使用同一身份提供方 | 以共享 subject 映射订单 | 商城计划、IdP 和全站登录改造条件 | 长期统一身份方案，成本和迁移风险最高 |
| H. 导入商城密码/密码哈希 | 试图沿用商城密码 | 与订单导入一起迁移 | 需要取得凭据 | 禁止采用；通常不可取得，也不符合安全边界 |

## 4. 各方案详细说明

### 4.1 AIOVE 邮箱 + 密码

用户注册 AIOVE 并设置密码，以后继续使用 AIOVE 邮箱和密码登录。订单获取必须额外完成 Shopify OAuth、邮箱认领或后台导入，因此“登录”和“订单证明”是两条链路。

优点：复用现有认证。
缺点：用户需要记新密码；不能自然证明其商城身份。
结论：保留兼容，不建议作为 FKK 导流用户的唯一入口。

### 4.2 AIOVE 邮箱验证码免密码登录

用户每次输入邮箱，由 AIOVE 发送一次性验证码；验证成功后创建或登录本地账号并签发 AIOVE session。后续登录仍使用验证码，不需要密码。

订单可在邮箱验证后按当前 `site_id` 查询，但必须处理同邮箱多客户、订单邮箱变化、游客结账和跨站点重复邮箱等情况。

优点：实现相对直接，不依赖 Shopify 客户账号模式。
缺点：验证码由 AIOVE 自己维护；仅能证明邮箱控制权，不天然得到 Shopify OAuth subject。
结论：适合作为可靠 fallback，也可以独立成为主登录方式。

### 4.3 Shopify Customer Account OAuth/OIDC

用户点击 `Continue with FootballKitUK` 等站点化入口，AIOVE 将用户跳转到该站点的 Shopify 客户授权端点。Shopify 完成邮箱验证码或其支持的登录方式后，把 authorization code 返回 AIOVE；AIOVE 校验 `state`、PKCE/secret、issuer、nonce 和回调地址，换取身份结果并建立本地 session。

以后登录仍点击同一按钮：Shopify 授权状态有效时可快速返回；状态失效时由 Shopify 再次验证。AIOVE 不接触 Shopify 密码。

AIOVE 仍需建立本地用户和外部身份映射，用于：

- 承接游客会话；
- 识别重复登录；
- 将 Shopify customer identity 对应到正确订单；
- 解绑、撤销、删除和审计；
- 防止同一外部身份绑定多个本地账号。

前置条件：

- FKK 已启用兼容的新版 Shopify Customer Accounts；
- 能获得 Customer Account API client ID，并配置精确 callback URL；
- 授权范围允许读取所需客户范围数据；
- 若使用 Admin API 补充订单，另行具备 `read_customers`、`read_orders` 及受保护客户数据条件；
- 明确 OAuth token 生命周期、刷新、撤销、登出和账号删除行为。

优点：用户不新增密码；Shopify 直接证明商城客户身份；登录和订单归属最自然。
缺点：依赖 Shopify 配置和账号模式；必须维护 OAuth 安全、token 和身份映射。
结论：与当前产品目标最贴合，但必须先做 FKK 可行性核验，不能仅凭文档存在就承诺可用。

官方参考：

- [Shopify Customer Account API](https://shopify.dev/docs/api/customer)
- [Shopify Customer Accounts](https://help.shopify.com/en/manual/customers/customer-accounts/new-customer-accounts)
- [Shopify Admin GraphQL Customer](https://shopify.dev/docs/api/admin-graphql/latest/objects/Customer)

### 4.4 一次性邮箱验证与订单认领

用户验证下单邮箱后，将该站点下的历史客户/订单数据一次性归入 AIOVE。完成后可以停止外部身份连接；用户以后通过选定的 AIOVE 登录方式进入。

优点：不依赖持续 OAuth；适合历史数据迁移。
缺点：必须另行决定后续登录方式和新订单同步方式；一次性认领不等于 SSO。
结论：适合 OAuth 不可用或只需要导入历史画像的情况。

### 4.5 预导入待认领账号

先把商城客户和订单导入为“外部客户档案/待认领数据”，但不直接创建可登录的正式 AIOVE 用户。用户验证邮箱后才创建或关联本地账号。

不应把全部商城客户直接写入 `users`，否则后台会出现大量从未访问 AIOVE 的假注册账号，统计、隐私删除和重复账号处理都会失真。

优点：首次认领后历史数据可立即使用。
缺点：全量客户数据提前进入 AIOVE，数据治理和清理成本更高。
结论：只有按需查询性能或 Shopify 限流不能满足时再考虑。

### 4.6 社交登录 + 独立订单认领

Google/Apple 只负责登录 AIOVE。即使社交邮箱与订单邮箱相同，也不能在没有商城授权或邮箱验证规则的情况下自动认领订单。

优点：登录体验成熟。
缺点：仍需第二步证明商城身份，可能造成流程重复。
结论：可作为通用 AIOVE 登录入口，不是商城订单归属方案。

### 4.7 共享身份提供方

FKK 与 AIOVE 都改为使用同一个 IdP，例如由统一 `sub` 识别用户。用户一次身份体系即可进入两边。

优点：长期身份最统一。
缺点：需要改造商城和 AIOVE 登录，受 Shopify 套餐/能力限制，迁移和回滚复杂。
结论：当前阶段过重，不作为首期方案。

### 4.8 密码或密码哈希导入

无论是否能取得，都不采用复制明文密码、密码哈希或让 AIOVE 收集商城密码再代为尝试登录的方案。不同系统的哈希策略、pepper、升级策略和风控无法安全等同，且会扩大凭据泄露风险。

结论：明确排除。

## 5. 推荐的候选组合（尚未批准）

若 FKK 可配置 Shopify Customer Account OAuth，优先评估以下组合：

1. 主入口：`Continue with FootballKitUK`，由 Shopify 完成客户身份验证。
2. OAuth 返回后：创建或登录 AIOVE 本地账号，原子承接当前游客会话。
3. 订单：以已验证 Shopify customer identity 拉取历史订单，保存可信来源并生成初步画像。
4. 新订单：首期可在登录时增量同步；后续再评估 Shopify webhook。
5. fallback：OAuth 不可用或客户没有可用身份时，使用 AIOVE 邮箱验证码；订单认领必须另行验证。
6. 兼容入口：保留现有 AIOVE 密码/Google 登录，不强制迁移已有用户。

这套组合中的“本地 AIOVE 用户 + 外部身份映射”是实现登录连续性和订单归属所必需的内部结构，不代表用户需要管理两个账号或两套密码。

## 6. 订单与画像的数据边界

建议最小原始数据：

- 来源：`site_id`、provider、external customer/order ID、同步时间；
- 订单：创建时间、支付/取消/退款状态、币种、金额；
- 商品行：商品/variant ID、SKU、名称、数量、尺码、可追溯商品引用；
- 不导入：支付凭据、完整支付信息和与画像无关的敏感字段。

画像可从可信订单推导球队、球员、球衣类型、常用尺码和购买时间偏好；每条画像需要来源订单引用、置信状态和更新时间。模型只能读取后端已确认的画像，不能把聊天猜测升级为“已购买”。

## 7. 实施前必须确认的问题

1. FKK 当前是新版还是旧版 Shopify Customer Accounts？
2. FKK 店铺是否能创建/配置 Customer Account API 客户端和 callback URL？
3. 当前 Shopify app/token 已具备哪些客户和订单 scopes？是否满足受保护客户数据要求？
4. Customer Account API 返回的订单范围是否覆盖业务所需历史订单和游客结账订单？不足部分是否允许用 Admin API 补充？
5. OAuth 失败、用户拒绝授权或 Shopify 客户身份不存在时，使用哪种 fallback？
6. 同一邮箱在 AIOVE 已有账号、同一 Shopify 身份已绑定其他账号时如何合并或拒绝？
7. 用户解绑、删除账号、撤销 Shopify 授权后，历史订单和推导画像如何保留或删除？
8. 新订单同步采用登录时增量、webhook、定时任务还是组合方式？
9. 多站点同邮箱是否始终保持独立商城身份与订单画像？
10. 后台需要展示哪些授权、同步、失败和人工处理状态？
