# 角色归属折扣码展示、表达与购买规格

状态：`Approved direction`（后台折扣码登记与管理已在本地实现；面向用户的查询、展示、AI 表达和购买自动应用尚未实现）

关联基础规格：[`2026-07-20-creator-performance-and-discount-codes.md`](./2026-07-20-creator-performance-and-discount-codes.md)

## 1. 目标

- 将后台已登记的 `site` / `creator` 折扣码按当前角色对象安全投放到正式用户链路。
- 支持一个前台或一个网红拥有多个同时有效的折扣码。
- 让产品详情、AI 回复和购买跳转复用同一套服务端资格判断。
- 保持游客不展示、不接收、不由 AI 发送折扣码的现有边界。
- 不让前端、模型或 URL 参数自行决定折扣码归属、有效性和适用站点。

## 2. 非目标

- 不通过 Shopify API 创建、修改或删除折扣码；管理员继续手动登记独立站已经存在的码。
- 不实现折扣码领取、核销回传、订单归因、佣金结算或一次性用户绑定。
- 不实现多个折扣码自动叠加。
- 不把 Search、Kitshop 等没有明确角色上下文的页面默认归属给某个网红或前台。
- 不重做现有 `promotion_campaigns.discount_code` 活动单码链路。

## 3. 核心业务规则

### 3.1 角色对象决定折扣码集合

#### 网红角色

当前角色为 `creator` 时，只允许展示和表达同时满足以下条件的折扣码：

- `site_id` 等于当前角色所属站点；
- `ownership_type = creator`；
- `creator_uid` 等于当前角色可信的 owner 账号；
- 折扣码已启用且处于有效期内。

不得展示其他网红的码，也不得默认混入站点前台码。

#### 前台角色

当前角色为 `mascot` 或当前站点前台时，只允许展示和表达同时满足以下条件的折扣码：

- `site_id` 等于当前前台所属站点；
- `ownership_type = site`；
- 折扣码已启用且处于有效期内。

不得展示网红专属码或其他站点的码。

### 3.2 多码规则

- 一个站点和一个网红均可登记多个折扣码。
- 产品详情可以展示当前角色对象下的全部有效码。
- 同一 code 在同一列表中忽略大小写去重。
- 列表使用稳定顺序：`updated_at DESC, code ASC`。
- 本期不增加“主推码”“优先级”或自动解析优惠力度字段。
- 多码不能同时自动应用；用户必须明确选择一个码后才能生成带码购买链接。

### 3.3 有效状态

面向用户返回的码必须满足：

```sql
is_enabled = 1
AND (starts_at IS NULL OR starts_at <= CURRENT_TIMESTAMP)
AND (ends_at IS NULL OR ends_at > CURRENT_TIMESTAMP)
```

未开始、已过期、已停用、站点停用、角色归属失效或跨站关系不一致的码不得返回。

### 3.4 游客边界

- 游客产品详情不展示折扣码。
- 游客提示词不注入折扣码。
- 游客 API 响应和持久化商品快照不得包含 `discountOffers`。
- 游客询问折扣时继续使用现有注册引导。
- 游客结账仍按现有认证边界拦截。

### 3.5 页面范围

首期只对有明确角色对象的产品详情生效：

- Chat 中角色发送的商品；
- 实时通话中当前角色发送的商品。

Search、Kitshop 的产品详情没有角色对象，首期不展示角色归属折扣码。后续如需展示，必须先定义这些页面代表哪个角色，不能使用默认前台或最近聊天角色隐式回退。

## 4. 产品详情体验

### 4.1 展示字段

每个折扣码展示：

- `code`；
- `offerDescription`；
- 归属文案，例如“Luna 专属优惠”或“Football Kit UK 优惠”；
- 复制按钮；
- “使用此优惠”选择操作。

后台 `notes`、创建人、更新人、内部 ID 和其他运营字段不得显示。

### 4.2 选择状态

- 默认不自动叠加任何码。
- 用户可选择一个有效码作为本次购买码。
- 切换选择时，只保留一个选中码。
- 再次点击当前已选码时取消选择。
- 未选择时，购买按钮打开带空 `discount=` 的可信 variant cart，明确清除上次 Checkout 折扣。
- 选中码在点击购买前必须由服务端重新校验。
- 假码、过期、停用或无法向 Shopify 确认时，生成明确清除折扣的链接，不继承旧页面状态。

### 4.3 旧单码兼容

- 现有商品对象中的 `code` / `discountCode` 继续支持。
- 有角色折扣码列表时，产品详情使用多码列表。
- 没有角色折扣码但活动商品自带旧单码时，保留原单码展示。
- 活动单码与角色码文本相同则去重。
- 活动单码只属于命中该活动的商品，不扩散到普通商品详情。

## 5. AI 表达规则

### 5.1 可信上下文

AI 只能使用后端筛选后注入的：

- 精确 `code`；
- 精确 `offerDescription`；
- 必要的有效期提示。

模型不得查询数据库、猜测折扣力度、改写 code、承诺不存在的优惠或引用后台备注。

### 5.2 对话行为

- 用户问“有没有折扣”：角色可按当前人设自然介绍一个可用码。
- 用户问“还有其他折扣吗”：可继续介绍同一角色对象下的其他有效码。
- 用户明确问“有哪些折扣码”：可以列出后端提供的当前有效码。
- 没有码时：不得暗示存在折扣。
- 产品跟进短句仍遵守现有规则，不在商品卡后重复朗读价格、库存、URL 和所有优惠码。
- 语音回复使用与文字相同的确定性折扣码上下文，不建立第二套筛选逻辑。

后端最多向单次模型请求提供 5 个有效码，避免把全部运营记录塞入提示词。

## 6. 购买自动应用

- 用户只能为一次购买选择一个折扣码。
- 前端不得自行将 code 拼入购买 URL。
- 服务端必须重新解析商品、当前用户、当前角色、站点和折扣码资格。
- 服务端还必须使用 Shopify `read_discounts` 核验码存在且状态为 `ACTIVE`。
- 只有 Shopify 站点且购买目标 URL 属于当前站点可信来源时，才尝试生成带码链接。
- 不支持安全自动应用、权限缺失或核验失败时使用空 `discount=` 清除旧码，同时保留复制码能力。
- 服务端不能确认自动应用成功时，不得向用户显示“已应用”。
- 正式实现前必须用当前独立站真实 cart/checkout 链接验证 Shopify 分享折扣链接的实际行为。

## 7. 数据接口

面向用户的安全折扣码 DTO：

```json
{
  "id": "discount_xxx",
  "code": "LUNA20",
  "offerDescription": "20% OFF",
  "ownershipType": "creator",
  "endsAt": "2026-12-31T23:59:59.000Z"
}
```

不自动生成归属展示文案，也不返回 `notes`、`createdBy`、`updatedBy` 或原始数据库关系对象。

## 8. 安全与确定性边界

- 用户身份从服务端 session 解析。
- `characterId` 只作为请求目标，服务端必须重新查询角色类别、owner 和站点。
- 前端提供的 `siteId`、`ownerUserId` 和角色类型不能决定折扣码归属。
- 历史商品消息不永久保存实时折扣码列表，避免过期码在旧会话中继续展示。
- 产品详情打开或刷新时读取当前有效码。
- 购买链接生成时再次读取并锁定当前有效码，不能复用前端旧状态。
- 跨站 URL、跨站角色、跨网红 code、过期 code 和伪造 code ID 必须确定性拒绝。

## 9. 验收标准

- 前台角色只展示当前站点的多个有效站点码。
- 网红角色只展示该网红账号的多个有效 creator 码。
- 切换角色后，旧角色折扣码不残留。
- Search、Kitshop 无角色上下文时不展示角色折扣码。
- 游客在产品详情、聊天、语音、历史和接口响应中都拿不到具体码。
- 过期、未开始、停用、跨站和错误归属码不返回。
- 产品详情支持多码复制、单码选择和失效提示。
- AI 只表达后端提供的真实 code 和优惠说明，并保持角色人设。
- 选中一个码后，只有服务端验证通过才生成带码购买链接。
- 原广告活动单码、产品卡、Search、Kitshop、实时通话和正式聊天不回归。
