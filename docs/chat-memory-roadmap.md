# 对话记录与用户画像推进方案

## 当前说明

- 2026-06-09 晚间起，`候选画像 / 候选审核` 这一整条线已不再作为当前版本继续推进方向。
- 原因：当前产品版本已经不再使用候选入口，这条线属于旧路线遗留。
- 处理原则：
  - 后台前端入口已下线。
  - 后台“用户记忆”页面、管理接口和 `admin-memory-*` 专用代码已清理。
  - 底层对话记录、正式用户画像、日 / 周 / 月提炼、历史检索链路继续保留。
  - 后续推进默认围绕：
    - 原始对话记录
    - 正式用户画像
    - 日 / 周 / 月提炼
    - 历史检索
    - AI prompt 使用链路
- 因此下面第 8 期到第 16 期有关候选的内容，仅作为历史记录保留，不再作为后续待办继续执行。
- 2026-06-09 晚间已进一步确认：用户未要求新增“用户记忆”后台管理页，因此该页面及对应管理 API 已从当前代码中移除。

## 目标

建立一套面向足球粉丝场景的对话数据体系，同时满足：

- 原始对话完整保留，可追溯、可审计、可重新提炼。
- AI 可以快速找到相关历史，不需要每次全量翻聊天记录。
- 用户画像从对话中结构化沉淀，并且每条画像都能反查来源。
- 日 / 周 / 月提炼作为阶段摘要，方便后台查看和 prompt 使用。

## 总体分层

### 1. 原始对话层

已有表：

- `chat_sessions`
- `chat_messages`

职责：

- 保存文本、附件、语音、商品卡等原始消息。
- 作为所有提炼、画像、检索的事实来源。
- 不被摘要或画像替代。

### 2. 原始记录索引层

新增表：

- `chat_message_index`

职责：

- 给原始消息生成轻量索引。
- 支持按关键词、话题、实体、情绪、意图、重要度快速筛选历史消息。
- 后续可扩展 embedding 语义检索。

### 3. 用户画像 / 结构化记忆层

新增表：

- `user_memory_records`
- `user_memory_links`

职责：

- 存储结构化用户画像。
- 一条画像一条记录，而不是塞进一个大 JSON。
- 画像可以是全局共享，也可以是某个 AI 对象专属。
- 每条画像通过 link 表反查来源消息。

### 4. 日 / 周 / 月提炼层

新增表：

- `conversation_summaries`
- `conversation_summary_links`

职责：

- 按天、周、月归档对话摘要。
- 摘要保留结构化 JSON 和可读文本。
- 摘要可以回查来源消息和会话。

## 用户画像类型白名单

初期只开放足球粉丝场景需要的类型：

- `identity`
  - 用户希望被怎么称呼、常用语言、地区 / 时区等。
- `favorite_club`
  - 用户支持或高频关注的球队。
- `favorite_player`
  - 用户喜欢或高频关注的球员。
- `favorite_league`
  - 用户常看的联赛或赛事。
- `watching_habit`
  - 看直播、看集锦、熬夜看球、赛前预测、赛后复盘等习惯。
- `interaction_preference`
  - 喜欢热血、嘴毒、专业分析、短句、朋友式聊天等。
- `football_emotion_trigger`
  - 主队输球、裁判争议、德比、转会传闻等足球相关情绪触发点。
- `ongoing_topic`
  - 当前持续讨论的球队、比赛、转会、战术、球员状态等。

暂不做：

- 主动提醒
- 梦境整理
- 泛心理诊断
- 复杂关系技能
- 带货购买画像

## 画像作用域

### 全局画像

`character_id` 为空。

适合记录：

- 支持球队
- 喜欢球员
- 常看联赛
- 看球习惯
- 语言偏好

### 角色专属画像

`character_id` 有值。

适合记录：

- 用户和某个角色的关系进展
- 用户更喜欢某个角色怎么说话
- 某个角色专属梗
- 某个角色内持续话题

## 写入规则

允许写入：

- 用户明确表达的稳定偏好。
- 用户明确说明的称呼和语言偏好。
- 反复出现的足球话题。
- 与当前角色持续相关的互动偏好。

谨慎写入：

- 一次性情绪吐槽。
- 暂时性看法。
- 不确定的推断。

禁止写入：

- 未确认的敏感隐私。
- 心理诊断式标签。
- 无事实依据的用户标签。
- 技术调试内容。

## Prompt 使用顺序

AI 回复时建议按顺序组合：

1. 角色人格：来自 `ai_characters`。
2. 最近原始对话：最近 8 到 12 条 `chat_messages`。
3. 高价值用户画像：从 `user_memory_records` 筛选。
4. 最近日提炼：从 `conversation_summaries` 取最新 `day` 摘要。
5. 相关历史原文：从 `chat_message_index` 命中后回表查原始消息。

## 日 / 周 / 月提炼

### 日提炼

优先上线。

建议字段：

- 今日主要话题
- 今日关键事件
- 今日新增或确认的足球偏好
- 今日主要情绪倾向
- 今日角色互动特点
- 下次可延续话题

### 周提炼

由 7 天日提炼压缩。

建议字段：

- 本周持续关注球队 / 球员 / 联赛
- 本周反复话题
- 本周情绪变化
- 本周新增稳定偏好
- 本周角色关系变化

### 月提炼

后置。

建议字段：

- 长期兴趣画像
- 稳定互动风格
- 稳定足球情绪触发点
- 长周期关注议题
- 用户与角色关系概况

## 分期推进

### 第 1 期：数据结构打底

目标：

- 新增表结构。
- 新增枚举和基础服务骨架。
- 不接复杂 AI 提炼。

范围：

- `chat_message_index`
- `user_memory_records`
- `user_memory_links`
- `conversation_summaries`
- `conversation_summary_links`

### 第 2 期：用户画像抽取

目标：

- 对用户新消息做轻量规则抽取。
- 先覆盖足球粉丝画像白名单。
- 每条画像可追溯来源消息。

当前实现：

- 已新增规则型足球画像抽取。
- 只对用户文本消息生效。
- 只在用户明确表达偏好、称呼、看球习惯或互动偏好时写入。
- 同类型、同摘要、同作用域的活跃画像会更新确认时间，不重复插入。
- 每条画像通过 `user_memory_links` 关联来源消息和会话。

当前覆盖：

- `identity`
- `favorite_club`
- `favorite_player`
- `favorite_league`
- `watching_habit`
- `interaction_preference`
- `football_emotion_trigger`
- `ongoing_topic`

暂未覆盖：

- AI 模型辅助抽取。
- 人工审核。
- 用户主动查看 / 删除画像。
- 历史消息回填画像。

### 第 3 期：日提炼

目标：

- 按用户 + 角色 + 日期生成日摘要。
- 日摘要可反查来源消息。
- prompt 接入最近日摘要。

当前实现：

- 已新增规则型日提炼服务。
- 用户发送文本消息并生成 AI 回复后，会刷新当天 `conversation_summaries`。
- 日摘要会通过 `conversation_summary_links` 关联来源消息。
- prompt 已新增 `User Context` 层，接入：
  - 高价值用户画像
  - 最近日提炼

当前限制：

- 日提炼暂为规则型，不使用 AI 模型。
- 日提炼只覆盖基础足球话题、偏好、情绪线索、互动偏好、可延续话题。
- 周 / 月提炼已进入第 5 期实现，日提炼仍然是最细粒度来源。

### 第 4 期：历史检索增强

目标：

- 根据当前用户消息命中相关历史原文。
- 接入 prompt。
- 后续评估 embedding 语义检索。

当前实现：

- 已新增轻量历史检索服务。
- 根据当前输入抽取关键词、足球话题、情绪标签。
- 从 `chat_message_index` 命中旧消息，再回表读取原始消息。
- prompt 已新增 `Relevant History` 层。
- 检索会排除已经在最近对话里的消息，避免重复塞上下文。
- 历史检索前会对当前会话缺失索引的旧消息做懒加载回填。

当前限制：

- 仍然是规则型检索，不是 embedding 语义检索。
- 当前只在单个用户 + 单个角色会话范围内检索。
- 无关键词、话题、情绪命中时不会只凭重要度返回消息，避免无关历史污染 prompt。

### 第 5 期：周 / 月提炼

目标：

- 基于日摘要生成周摘要。
- 数据量足够后生成月摘要。

当前实现：

- 已新增规则型周 / 月提炼。
- 用户发送消息并生成 AI 回复后，会刷新：
  - 当天日摘要
  - 当前周摘要
  - 当前月摘要
- 周 / 月摘要写入 `conversation_summaries`，并通过 `conversation_summary_links` 关联来源原始消息。
- prompt 的 `User Context` 层已接入最近周摘要和最近月摘要，作为长期上下文补充。

当前限制：

- 周 / 月摘要仍然是规则型提炼。
- 已有后台查看和手动重算入口。
- 当前没有定时任务，刷新依赖用户消息触发。

### 第 6 期：后台查看入口

目标：

- 管理员可以查看当前库内的用户画像、对话提炼和索引统计。
- 先只做只读入口，避免误删或误改用户记忆。

当前实现：

- 已新增 `/api/admin/memory` 只读接口。
- 后台新增“用户记忆”页面。
- 页面展示：
  - 活跃画像数量
  - 活跃摘要数量
  - 已索引消息数量
  - 已产生画像的用户数量
  - 用户画像列表
  - 日 / 周 / 月提炼列表
- 已支持基础筛选：
  - 用户邮箱 / 昵称关键词
  - 角色
  - 用户画像类型
  - 摘要周期
- 已支持时间范围筛选：
  - 最近 7 天
  - 最近 30 天
  - 最近 90 天
- 已支持自定义日期范围：
  - 开始日期
  - 结束日期
  - 自定义日期优先于固定时间范围
- 已支持基础分页：
  - 返回当前页
  - 每页数量
  - 总页数
  - 画像总量
  - 摘要总量
- 角色筛选选项已改为接口动态返回，不再写死前端角色列表。
- 接口只允许管理员访问，未登录或非管理员不能读取。
- 已支持可控管理操作：
  - 用户画像内容编辑
  - 用户画像软归档
  - 归档画像查看
  - 归档画像恢复
  - 日 / 周 / 月提炼手动重算

当前限制：

- 暂时不做用户画像物理删除，默认以归档保留追溯。
- 暂时不支持直接输入页码跳页。

### 第 7 期：后台维护工具

目标：

- 管理员可以在当前筛选范围内手动维护记忆数据。
- 当历史数据、索引、画像或摘要出现缺口时，可以按用户 / 角色 / 时间范围补齐。
- 维护操作必须有范围和数量上限，避免误扫全库。

当前实现：

- 已新增 `POST /api/admin/memory/rebuild-indexes`。
- 已新增 `POST /api/admin/memory/rebuild-summaries`。
- 后台记忆服务已按职责拆分：
  - `admin-memory-service.js`：统一导出口。
  - `admin-memory-overview-service.js`：统计、筛选、列表读取。
  - `admin-memory-actions-service.js`：画像归档 / 恢复 / 编辑、单条提炼重算。
  - `admin-memory-maintenance-service.js`：批量补索引、回填画像、重建提炼。
  - `admin-memory-utils.js`：筛选、分页、映射和维护工具函数。
- 后台“用户记忆”页面新增两个维护按钮：
  - `补索引 / 回填画像`
  - `重建日周月提炼`
- 两个维护动作都会复用当前页面筛选条件：
  - 用户邮箱 / 昵称
  - 角色
  - 最近 7 / 30 / 90 天
  - 自定义开始 / 结束日期
- 索引维护会扫描符合范围的已发送消息：
  - 补齐 `chat_message_index`
  - 对用户文本消息尝试规则型画像回填
- 摘要维护会按会话日重建：
  - 日提炼
  - 对应周提炼
  - 对应月提炼

当前限制：

- 维护工具仍使用规则型索引、画像和摘要逻辑。
- 没有接入自动定时任务。
- 没有做批量删除或物理清理。
- 大范围历史重算需要分批执行，不建议一次性扫全库。

### 第 8 期：AI 画像候选审核流

目标：

- 在规则型画像之外，引入 AI 辅助提炼能力。
- 但 AI 不直接写正式画像，先生成待审核候选，避免脏数据直接进入 prompt。
- 管理员可以在后台查看、通过或拒绝候选。

当前实现：

- 已新增 `user_memory_candidates` 表。
- 已新增 AI 候选生成服务：
  - `server/chat-memory-candidate-service.js`
- 已新增管理员接口：
  - `POST /api/admin/memory/generate-candidates`
  - `PATCH /api/admin/memory-candidates/:id/approve`
  - `PATCH /api/admin/memory-candidates/:id/reject`
- 后台用户记忆页已按职责拆分：
  - `admin-memory-content.js`：用户记忆页 HTML 和卡片渲染。
  - `admin-memory-page.js`：用户记忆页数据加载、筛选、维护按钮和审核交互。
  - `admin-memory-actions.js`：用户记忆页维护按钮、批量审核、单条操作和编辑弹窗。
- 后台“用户记忆”页新增：
  - `画像候选` 面板
  - `AI 生成候选` 按钮
  - 候选通过 / 拒绝操作
  - 当前页候选批量通过 / 批量拒绝
- AI 候选生成规则：
  - 只读取用户文本消息
  - 只允许白名单画像类型
  - 模型输出必须是严格 JSON
  - 候选先进入 `pending`，不会直接成为正式画像
- 候选审核规则：
  - 通过：写入 `user_memory_records`
  - 拒绝：只更新候选状态并保留审核记录

当前限制：

- AI 候选当前只通过后台维护按钮触发，不在用户每次发消息后自动调用。
- 候选仍然依赖管理员审核，不会自动入 prompt。
- 批量审核当前只处理当前页候选，不跨页处理全库候选。

### 第 9 期：候选画像质量检测

目标：

- 管理员审核 AI 候选画像时，能先看到质量提示。
- 避免重复画像、疑似冲突画像、低可信度画像直接通过。
- 质量判断只做审核辅助，不自动拒绝、不自动改正式画像。

当前实现：

- 已新增候选质量判断模块：
  - `server/admin-memory-quality-service.js`
- 后台总览接口读取候选后，会和同用户、同类型、同作用域、同角色的有效画像比较。
- 后端会返回：
  - `qualityFlags`：质量标签。
  - `conflictCount`：关联画像数量。
  - `conflicts`：最多 3 条关联有效画像摘要。
- 当前质量标签：
  - `可能重复`：候选摘要或内容与已有有效画像一致。
  - `可能冲突`：单值型画像下，候选和已有画像属于同一桶但内容不同。
  - `已有同类`：多值型画像下，已有同类画像，可供管理员判断是否继续通过。
  - `低可信度`：候选可信度低于 60。
  - `低重要度`：候选重要度低于 50。
- 后台“画像候选”卡片已显示质量标签和第一条关联画像。

当前限制：

- 冲突判断仍是规则型，不做复杂语义推理。
- 当前不会自动合并相似画像。
- 当前不会自动拒绝低质量候选，仍由管理员决定。

### 第 10 期：候选来源消息预览

目标：

- 管理员审核 AI 候选画像时，可以直接看到候选来源的原始对话片段。
- 减少只看 AI 摘要造成的误判。
- 保持原始消息可追溯，不用摘要替代原文。

当前实现：

- 后台记忆总览接口读取候选时，已关联 `chat_messages`。
- 候选返回新增：
  - `sourceMessagePreview.id`
  - `sourceMessagePreview.senderType`
  - `sourceMessagePreview.contentType`
  - `sourceMessagePreview.text`
  - `sourceMessagePreview.sentAt`
- 来源文本在接口层限制为最多 180 字符，避免后台卡片被长消息撑开。
- 后台“画像候选”卡片已显示：
  - 来源对话文本
  - 消息发送方
  - 消息类型
  - 消息时间

当前限制：

- 当前只展示候选直接关联的一条来源消息。
- 如果候选没有 `source_message_id`，不会显示来源预览。
- 暂未做完整来源消息弹窗，后续可在详情页展示更多上下文。

### 第 11 期：候选来源上下文查看

目标：

- 管理员审核候选画像时，可以查看来源消息前后几轮对话。
- 避免只看单句来源导致误判。
- 继续保持候选画像可追溯、可审核、可人工判断。

当前实现：

- 已新增只读接口：
  - `GET /api/admin/memory-candidates/:id/context`
- 已新增服务模块：
  - `server/admin-memory-context-service.js`
- 接口会读取：
  - 候选画像基础信息。
  - 来源消息 ID。
  - 来源会话 ID。
  - 同会话内来源消息前 3 条。
  - 来源消息自身。
  - 同会话内来源消息后 3 条。
- 后台“画像候选”卡片新增：
  - `查看上下文` 按钮。
- 点击后弹窗展示：
  - 候选摘要。
  - 用户 / 角色信息。
  - 来源上下文消息列表。
  - 来源消息高亮。

当前限制：

- 当前上下文窗口固定为前 3 条、后 3 条。
- 如果候选没有来源消息，会返回不可查看。
- 当前只读展示，不支持在弹窗内直接编辑候选或画像。

### 第 12 期：候选编辑后再通过

目标：

- 管理员审核候选画像时，不需要只能二选一通过 / 拒绝。
- 允许管理员先修正候选摘要、候选内容和评分，再决定是否通过。
- 确保正式画像写入的是人工修正后的版本，而不是 AI 原始候选版本。

当前实现：

- 已新增管理员接口：
  - `PATCH /api/admin/memory-candidates/:id`
- 已支持编辑字段：
  - `summary`
  - `content`
  - `importanceScore`
  - `confidenceScore`
  - `freshnessScore`
- 限制：
  - 只允许编辑 `pending` 状态候选。
  - 已通过或已拒绝候选不能再编辑。
- 后台“画像候选”卡片已新增：
  - `编辑候选` 按钮。
- 后台候选编辑弹窗已接入：
  - 编辑后刷新列表。
  - 后续通过候选时，会把编辑后的内容写入正式画像。

当前限制：

- 当前只能编辑候选的文本和分数，不支持改画像类型、作用域、角色归属。
- 当前编辑弹窗不显示候选来源上下文，需要先关掉弹窗后再看上下文。
- 当前没有单独的候选编辑审计表，暂时以 `updated_at` 和审核记录为主。

### 第 13 期：候选编辑审计

目标：

- 记录管理员每次编辑候选画像的前后内容。
- 后续多人管理时可以追溯“谁在什么时候改过候选”。
- 避免候选被人工修正后无法判断原始 AI 输出和人工修改差异。

当前实现：

- 已新增表：
  - `user_memory_candidate_audits`
- 审计字段包括：
  - `candidate_id`
  - `edited_by`
  - `action_type`
  - `before_json`
  - `after_json`
  - `created_at`
- `PATCH /api/admin/memory-candidates/:id` 已改为事务执行：
  - 读取候选旧值并锁定。
  - 更新候选内容和评分。
  - 写入编辑审计记录。
- 审计记录跟随候选删除级联清理。

当前限制：

- 当前只记录候选编辑动作，不记录通过 / 拒绝动作的完整 before / after。
- 当前后台还没有单独展示审计列表。
- 当前审计记录主要供数据库排查和后续后台展示扩展使用。

### 第 14 期：候选审核动作审计

目标：

- 记录候选通过和拒绝动作。
- 补齐候选从生成、编辑到最终审核的完整操作轨迹。
- 让正式画像来源不仅能追到候选，也能追到候选是由谁审核通过的。

当前实现：

- `approveMemoryCandidate` 已改为事务执行：
  - 锁定待审候选。
  - 创建正式用户画像。
  - 更新候选状态为 `approved`。
  - 写入 `user_memory_candidate_audits` 审计记录。
- `rejectMemoryCandidate` 已改为事务执行：
  - 锁定待审候选。
  - 更新候选状态为 `rejected`。
  - 写入 `user_memory_candidate_audits` 审计记录。
- 审计记录会写入：
  - `action_type = approve`
  - `action_type = reject`
  - 操作人 ID。
  - 操作前候选快照。
  - 操作后状态。
  - 通过动作额外记录生成的正式画像 ID。
- 批量通过 / 批量拒绝沿用单条审核函数，因此每条候选都会分别写审计。

当前限制：

- 后台暂未展示审计列表。
- 审计表字段名仍为 `edited_by`，当前复用为候选操作人。
- 审计记录会随候选删除级联删除；现阶段候选本身不做物理删除。

### 第 15 期：候选审计后台展示

目标：

- 让管理员可以在后台查看候选操作轨迹。
- 审核候选时同时看到来源上下文和候选编辑 / 通过 / 拒绝记录。
- 避免审计数据只停留在数据库里，后台无法使用。

当前实现：

- `GET /api/admin/memory-candidates/:id/context` 已返回：
  - `audits`
- 每条审计包含：
  - 操作 ID。
  - 候选 ID。
  - 操作人 ID。
  - 操作人邮箱。
  - 操作人昵称。
  - 操作类型。
  - 操作前快照。
  - 操作后快照。
  - 操作时间。
- 后台“查看上下文”弹窗已新增：
  - `操作记录` 区块。
  - 编辑候选记录。
  - 通过候选记录。
  - 拒绝候选记录。
- 如果候选没有审计记录，会显示暂无候选操作记录。

当前限制：

- 审计记录目前只在候选上下文弹窗中展示。
- 还没有单独的全局审计筛选页。
- 编辑记录目前优先展示摘要变化；更细的字段 diff 后续可继续增强。

### 第 16 期：候选审计字段级展示

目标：

- 管理员查看候选审计时，可以看清楚每次编辑具体改了哪些字段。
- 避免只展示摘要变化，导致内容或评分调整不明显。
- 让候选审核记录更适合排查和交接。

当前实现：

- 后台候选上下文弹窗的“操作记录”已增强字段级展示。
- 编辑候选记录会逐项展示实际变化：
  - 摘要
  - 内容
  - 可信度
  - 重要度
  - 新鲜度
- 未变化字段不会显示，减少噪音。
- 长文本会自动截断，避免撑开弹窗。
- 通过 / 拒绝记录保持原展示：
  - 通过：展示正式画像 ID。
  - 拒绝：展示不会写入正式画像。

当前限制：

- 字段级变化仍是摘要式文本，不是左右对照 diff。
- 长文本只显示前 48 字符，完整内容仍需查看审计 JSON 或候选内容。
- 审计记录仍只在候选上下文弹窗中展示。

## 后续完整执行清单

### A. 对话记录

- 保持 `chat_messages` 作为原始事实层，禁止用摘要覆盖原文。
- 对文本、图片、文档等消息分别保存类型和附件信息。
- 所有后续画像、摘要、索引都必须能反查原始消息。

### B. 原始记录索引

- 继续使用 `chat_message_index` 给原始消息建立检索入口。
- 短期使用规则关键词、足球实体、情绪、意图和重要度。
- 中期评估 embedding 语义检索，但不在当前阶段引入新依赖。
- 管理后台保留重建索引能力，用于修复历史数据缺口。

### C. 用户画像

- 正式画像继续使用 `user_memory_records`。
- 来源关系继续使用 `user_memory_links`。
- AI 生成内容先进入 `user_memory_candidates`，审核通过后才进入正式画像。
- 画像类型继续围绕足球粉丝场景：
  - 身份信息
  - 喜欢球队
  - 喜欢球员
  - 关注联赛
  - 看球习惯
  - 互动偏好
  - 足球情绪触发点
  - 进行中话题

### D. 日 / 周 / 月提炼

- 日提炼用于当天对话压缩。
- 周提炼用于观察连续关注的话题和偏好。
- 月提炼用于长期画像辅助。
- 摘要必须保留来源消息关系，方便人工追溯。
- 后续可以补定时任务，但当前仍以用户消息触发和后台手动维护为主。

### E. AI Prompt 使用

- AI 回复时按顺序使用：
  1. 角色人格。
  2. 最近原始对话。
  3. 有效用户画像。
  4. 日 / 周 / 月提炼。
  5. 相关历史原文。
  6. 当前用户输入。
- 候选画像未通过前不能进入 prompt。
- 低质量或归档画像不能进入 prompt。

### F. 后台管理

- 管理员必须能查看画像、摘要、候选和来源数量。
- 管理员必须能编辑、归档、恢复正式画像。
- 管理员必须能通过或拒绝候选画像。
- 管理员必须能按筛选范围补索引、回填画像、重建提炼。
- 后续可补：
  - 候选详情弹窗。
  - 来源消息查看。
  - 画像合并。
  - 管理员审核操作日志。

### G. 质量控制

- 已完成基础候选质量提示。
- 已完成候选来源消息预览。
- 已完成候选来源上下文查看。

- 已完成候选编辑审计。
- 已完成候选审核动作审计。
- 已完成候选审计后台展示。
- 已完成候选审计字段级展示。
- 下一步可继续补：
  - 画像合并建议。
  - 候选字段扩展评估。
  - 明确相反偏好检测。
  - 长期未确认画像过期提醒。
  - 人工修正后的重新评分。
